ARCHITECTURE / THE SYSTEM BENEATH THE PRODUCT

Built like a platform.
Not a panel.

The architecture is deliberately split so the core can stay generic while game adapters, storage providers and orchestration integrations evolve independently.

01 / BOUNDARIES

Strong boundaries
keep the core clean.

Kubernetes objects should not leak everywhere. Game-specific conditions should not leak everywhere. Storage vendors should not leak everywhere.

CONTROL PLANE

Domain + API

Servers, tasks, users, permissions, templates, desired state and orchestration intent.

GAME SDK

Game intelligence

Install, update, config, capabilities, console parsing, health checks and backup paths.

KUBERNETES LAYER

Infrastructure translation

Pods, services, PVCs, secrets, logs and events behind a dedicated service boundary.

02 / RECONCILIATION

Desired state
is the source of truth.

The system continuously reasons about what should be true versus what is true right now.

USER INTENT

desiredState = RUNNING

The user asks for the outcome, not a specific sequence of commands.

RECONCILE

actualState = STOPPED

The worker identifies the difference and creates the required task.

ORCHESTRATE

Kubernetes workload starts

Infrastructure is created idempotently.

VERIFY

Game adapter health check passes

Actual state becomes RUNNING only when the game itself is considered healthy.

03 / ADAPTER CONTRACT

One SDK.
Infinite game shapes.

The adapter is the reason a future game can be added without rewriting scheduler, auth, tasks, storage or the dashboard shell.

interface GameAdapter {
  metadata(): AdapterMetadata
  capabilities(): CapabilitySet
  serverDefinition(input): WorkloadDefinition
  install(ctx): TaskPlan
  update(ctx): TaskPlan
  healthCheck(ctx): HealthResult
  parseConsole(line): GameEvent | null
  backupDefinition(): BackupDefinition
}

// Core does not care whether this is Minecraft, FiveM or a future game.
